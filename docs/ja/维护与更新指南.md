# 運用と更新

プログラム、埋め込みページ、実行データ、署名鍵、問題データ、設定を管理します

## バックアップ

開発環境は `make backup`。別の保存先は環境変数で指定します。コンテナーでは app 内のバックアップコマンドを使います

```bash
UMA_DATA_DIR=/srv/umaguess/runtime \
UMA_BACKUP_DIR=/srv/umaguess/backups \
go run ./cmd/server backup
```

```bash
docker compose exec app /app/uma-server backup --dir /backups
```

アプリの整合性バックアップを使用し、稼働中の SQLite 主ファイルだけをコピーしないでください。`verified-keys.json` とデプロイ設定は別途保存します

## プログラムの更新

```bash
make web-install
make web-build
make embed-spa
make embed-spa-check
make content-compile
make content-verify
make build
```

保存先を維持してサービスを再起動します。コンテナーは `docker compose up -d --build` を使用します。同じ保存先を複数のプロセスで開かず、スキーマ移行は起動時に行います

## 問題データの更新

出典データを変更後にビルドと検証を実行します。`content/current` を新しいパックに更新し、アプリを再起動します。公開済みパックは直接上書きせず、復元用に旧パックを保持できます

新しいパックは独立した実行ディレクトリーで確認し、`current` とファイルのハッシュを照合します。旧パックと設定を保持し、切り替え後にヘルス状態と対局開始を確認します。接続障害への対処として署名鍵を削除しないでください

復元前に独立したディレクトリーで SQLite の整合性、鍵、問題データの版、実行ユーザーのファイル権限を確認します。サービスの停止後に実行データを置き換えます。再接続の成功に加え、旧認証情報と旧接続のアクセス権が失効したことも確認します

## 復元

サービスを停止し、障害時のデータを保全してからバックアップを戻します。スキーマ移行後のデータを旧プログラムで読める保証はありません。旧プログラム、移行前バックアップ、対応する問題データと設定を一式で戻します

WAL／SHM や Docker ボリュームを削除して障害を解消しようとしないでください

## トラブル対応

| 症状 | 対処箇所 |
| --- | --- |
| 操作が拒否される | Origin の完全一致、HTTPS と Secure Cookie |
| スマートフォンから接続不可 | 待ち受け、ファイアウォール、同一 LAN、localhost の誤用 |
| 画面が古い | 再ビルド、埋め込みページ更新、再起動 |
| ready にならない | current、ファイルのハッシュ、権限 |
| 再接続が続く | SSE バッファリング、アイドル制限、接続上限、回線切り替え |
| SQLite locked | 重複起動、共有ディスク、ディスク遅延 |
| 種目を開始できない | デプロイ設定、人数、問題データのレポートと確認状況 |
| Turnstile が失敗し続ける | ホスト名、サイトキー、秘密鍵の受け渡し、外向き TLS、操作名 |
| 一人用の記録がない | URL、ブラウザー、サイトデータ削除、書き出しファイル |

## ログと権限

`/health/live` は生存確認、`/health/ready` は提供可能状態です。`/metrics` は既定でループバックに制限されます。プロキシでも外部アクセスを制限してください。ログに Cookie、認証情報、答え、完全な指紋を含めません

接続の本人性は既定で 30 秒ごとに再確認し、退出と参加枠の復元では旧接続を失効します。一時的な DB 障害による遅延や切断を、リタイア扱いにはしません
