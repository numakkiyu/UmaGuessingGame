# 维护与更新

维护对象包括应用二进制或镜像、前端嵌入资源、运行数据、签名密钥、内容包及部署配置。只备份 SQLite 主文件或只替换页面都不足以完成可靠更新

## 一致性备份

源码开发实例：

```bash
make backup
```

`make backup` 默认对应 `.cache/runtime`。维护其他目录时显式指定：

```bash
UMA_DATA_DIR=/srv/umaguess/runtime \
UMA_BACKUP_DIR=/srv/umaguess/backups \
go run ./cmd/server backup
```

容器：

```bash
docker compose exec app /app/uma-server backup --dir /backups
```

检查命令输出，确认备份文件存在并记录摘要。备份卷与运行卷分开，但同一机器上的两个卷仍不能抵御整机故障；应按自己的保留策略加密复制到受控的其他位置

`verified-keys.json` 是独立文件，保护与恢复规则见[安全策略](https://github.com/numakkiyu/UmaGuessingGame/blob/main/SECURITY.md)。恢复前确认备份命令实际包含哪些文件，不假定数据库备份自动覆盖所有外部配置、内容与密钥

## 更新程序

源码或二进制部署：

```bash
make web-install
make web-build
make embed-spa
make embed-spa-check
make content-compile
make content-verify
make build
```

随后按服务管理方式重启，运行目录须与之前一致。不要将源码的默认开发目录误当成线上数据位置

容器部署：

```bash
make content-compile
make content-verify
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 app
```

同一数据目录同时只能有一个服务进程，不能用第二个实例抢占文件实现无停机更新。SQLite 迁移属于启动流程，已应用迁移文件不改写，表结构变更通过新增迁移实现

## 内容更新

资料按来源快照、人工修订、编译产物三个层次维护。修改 `data/` 后先审查差异与来源，再编译并验证，不在运行时抓取外站替代校验

```bash
go run ./cmd/content build --dry-run
go run ./cmd/content build --out content
go run ./cmd/content verify
go run ./cmd/content sections
```

`content/current` 指向发布包。发布完成后重启服务，使新进程按选定内容加载；保留旧内容直到确认没有恢复或回滚需求。不要在正在使用的包目录里直接覆盖 section 或图片，否则 manifest 校验与版本含义会失效

## 恢复与回滚

先停止应用，保全故障数据及日志，再在独立目录检验备份的 SQLite 完整性、密钥和内容版本。仅在服务停止后替换运行数据，确认目录权限属于实际运行用户，再启动服务

若新版本已执行表结构迁移，不保证旧二进制能读取新数据库。回滚应成套恢复旧应用、迁移前备份、匹配的内容包与配置，不承诺自动降级迁移。不要随意删除 WAL/SHM 处理数据库问题，也不要在故障时执行删除卷命令

## 常见问题

| 现象 | 优先检查 |
| --- | --- |
| 页面能打开，操作被拒绝 | 地址是否与允许 Origin 完全一致，代理与 Secure Cookie 是否匹配 |
| 手机打不开 | 监听地址、防火墙、同网段、是否误用 localhost |
| 改了页面但仍显示旧版 | 是否重建 web、替换嵌入目录并重启二进制，浏览器缓存是否已更新 |
| 服务存活但未就绪 | 内容 current 指针、校验和、关键题库与目录权限 |
| 重连频繁 | 代理是否缓冲 SSE、空闲超时、连接上限、重复标签页与网络切换 |
| 某玩法无法开局 | 部署开关、玩法人数、内容报告、未审校数据及前端入口条件 |
| SQLite locked / 目录锁错误 | 是否误启多个进程、运行目录是否在共享磁盘、事务及磁盘延迟 |
| Turnstile 一直失败 | 主机名、站点键、secret 透传、出站 TLS 与操作名 |
| 练习记录不见了 | 浏览器数据是否被清理、是否换了域名/端口/浏览器，是否有导出文件 |

## 日志与监控

`/health/live` 判断进程存活，`/health/ready` 判断可提供服务，`/metrics` 用于受控监测。反向代理禁止公开指标，日志按保留周期管理并去除 Cookie、完整指纹、验证码和秘密答案

监控连接数、队列拒绝、写事务延迟、磁盘空间及恢复失败。发生限流时先定位异常来源与容量瓶颈，不以无限提高阈值代替修复。压测必须隔离实例，测试结束释放会话、连接和临时数据

## 连接权限维护

备份时核对运行目录中的 `verified-keys.json`。不要删除密钥迫使服务生成新文件，否则未过期凭据可能无法恢复

更新连接授权逻辑后，重启应用并验证旧会话退出、恢复码换设备、成员撤销与角色变化。确认旧设备断开、新设备保留原进度，其他房间和正常请求不被误撤销；仅测试重新连接不能证明旧长连接已失去访问权

默认实时身份复核周期为 30 秒，退出与席位恢复另外触发主动撤权。短暂数据库故障可能延迟周期撤权，需监控查询失败并恢复存储服务，不能将其自动转换为玩家判负。应用的请求限流不替代公网入口的 TLS、连接限制与洪泛防护，也不保证抵御分布式攻击
