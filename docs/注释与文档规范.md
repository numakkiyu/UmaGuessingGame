# 注释与公开文档规范

本规范用于当前 V2 的源代码与 GitHub 文档。GitHub 没有跨语言统一的“标准注释语法”，代码按语言官方约定，Markdown 按仓库阅读和维护需要组织

## 先判断有没有必要

代码能清楚表达的赋值、分支、返回和类型，不再用注释重复。值得保留的内容包括非显然的行为契约、并发顺序、生命周期、兼容限制、单位、信任边界和有依据的设计原因

```ts
// Preserve source order because the API matches items by position
const ordered = entries;
```

这类原因必须有实际接口约定支持，不能为了让注释显得重要而虚构安全、性能或历史理由。实现注释尽量短，说明约束及原因；声明文档只在调用者需要额外语义时使用

## 不应进入长期源码的内容

- 实现过程、内部协作安排和完成情况汇报
- 只能在本地打开的需求编号、私有会话链接和旧截图记录
- 已过时的数据数量、功能状态和曾经失败后如何修复的长篇叙事
- 与代码重复的章节标签、编号式步骤和夸张强调
- 没有可操作内容的 TODO、已经完成的 FIXME、整段注释掉的旧实现

发现真正未完成的功能时，不用美化注释掩盖：保留准确限制，建立可追踪的问题及验收条件。调查记录可以进入内部工作区，源码只保留维护者需要知道的当前约束

## 按语言书写

### Go

包与必要的导出声明按 [Go Doc Comments](https://go.dev/doc/comment) 编写，声明文档通常以名称开头，使用完整句子。说明参数单位、零值、错误、事务或并发契约，不逐字段翻译结构体名称

实现注释可用简短语句。`//go:embed`、`//go:build`、生成文件标记、许可与版权头保留其语法和位置。已应用的 SQL 语句保持不可变；必要的注释修订必须逐项兼容原始校验和，并测试拒绝未知改动

### TypeScript / JavaScript

采用必要的 JSDoc / TSDoc，不机械填充 `@param`、`@returns` 或 `@example`。类型系统已经表达的信息不重复，额外说明可观察行为、返回 `null` 的条件、缓存、取消与恢复等语义

解析评论时要分清真实注释与字符串、正则、JSX、模板中的数据。ESLint、覆盖率、构建和优化指令属于工具契约，不能当普通文字删除；生成的 API 类型应从契约重新生成，不直接清理

### CSS、Shell 与配置

CSS 注释说明层叠顺序、可访问性、空间预留及动效约束，不把设计讨论整篇搬进样式表。Shell 保留 shebang 与工具指令；Make 帮助注释、示例中禁用的可选配置、许可证头需按实际用途保留

单行实现注释可不加句末标点；多句声明文档按语言惯例使用正常标点。不能将玩家页面的文案标点偏好机械套用到 API 文档、代码字面量或编译指令

## 公开 Markdown

每份文档先说明读者、适用范围和操作结果，再给出前提、步骤、验证及失败处理。命令注明运行目录，代码块写语言标签，相对链接指向公开存在的文件，不依赖被 Git 忽略的资料

依赖版本以锁文件为准，默认值以实现及配置为准；行为变更同时更新示例。区分“已有代码”“内容准入”“自动测试通过”“真实设备验证”，不发布没有依据的完成百分比或性能承诺

公共资料应覆盖使用、架构、配置、规则、贡献、许可和运维。资料获取脚本、临时文档、执行计划、原始网页缓存和内部证据不加入公共项目；构建输入、人工审校台账、来源清单和长期测试工具继续随代码维护

文档变更保持可追溯，历史资料与现行操作说明分开维护，避免混用不同架构的数据库、框架或命令

## 验证方法

注释整理先用语言解析器定位，再比较修改前后的有效 token；不能用跨文件正则删除所有 `//` 或 `/* */`。格式化、类型检查与测试之后复核指令、生成文件和迁移摘要，说明真正的例外改动

文档检查相对路径、图片、命令与配置名，构建不需要内部目录。链接检查无法证明外部资料许可或题目事实，需要单独审查。不要为追求“零注释”删除必要约束，也不要为追求“文档覆盖率”给每个函数增加套话
